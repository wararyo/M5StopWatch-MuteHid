# 省電力化のアイデア集

作成日: 2026-09-10 / 更新日: 2026-09-19 / 版: 0.9（案1の電池駆動の測定結果を追加）

[仕様書](specification.md)の対象機（M5StopWatch）で、バッテリー・電源IC・MCUを交換せずにファームウェアだけで電池持ちを改善する案をまとめる。効果の見立てはすべて推定であり、実測で置き換える。

## 1. 現状の電力面の特徴

コード読解時点の実装（commit `0f8a54f` 相当）で、電力に関係する挙動は次のとおり。

| 項目 | 現状 | 根拠 |
|---|---|---|
| CPU クロック | 240 MHz 固定（案16で 80 MHz 固定に変更済み）。PM 無効、tickless idle 無効（案15で両方とも有効化済み） | `sdkconfig.defaults`、`CONFIG_PM_ENABLE` 未設定 |
| BT コントローラ | modem sleep 無効（案2で有効化済み。低速クロックは main XTAL） | `CONFIG_BT_CTRL_MODEM_SLEEP` 未設定 |
| メインループ | 10 ms 周期で常時ポーリング。暗転中もタッチの I2C 読み出しと描画判定を実行 | `src/app/MuteApp.cpp` の `vTaskDelay(pdMS_TO_TICKS(10))` |
| 画面 | 30 秒無操作で輝度 1/4（下限 15）へ暗転。消灯はしない | `IdleDimMs`、`applyBrightness()` |

| 接続パラメータ | 更新要求なし。slave latency なし（案1で要求を追加済み。macOS 相手の実測は 15 ms・latency 4） | `src/ble/TelephonyHid.cpp` |

## 3. 各案の詳細

### 3.1 無線（BLE）

**1. 接続パラメータ更新で slave latency を要求する。**（適用済み）暗号化完了後に `esp_ble_gap_update_conn_params` で、接続間隔 30〜45 ms（Apple のガイドラインに合わせ 15 ms の倍数）、latency 4、supervision timeout 4 s を要求する（`requestSlowLink()`）。本機からの送信（ボタン→PC）は latency に関係なく次の接続イベントで送れるため、操作の遅延は増えない。PC→本機の Output 反映だけが最大で (latency+1)×間隔 = 225 ms 遅れる。

実測（2026-09-18、macOS）: 接続直後のパラメータは 30 ms・latency 0・timeout 720 ms で、1 秒後に macOS が **15 ms・latency 0** に更新する。つまり適用前は無線が 15 ms ごと、1 秒に 67 回起きていた。要求を出すと macOS は一度そのまま受理し（45 ms・latency 4・4 s）、数秒後に自分の値 **15 ms・latency 4・720 ms** で上書きする。latency に 14 を要求しても同じく 4 に戻されるので、macOS 相手では要求値によらず「15 ms・latency 4」になる。これでも待機中の無線の起床は最大 75 ms ごとまで減る。Windows は未確認で、要求値をそのまま受ける可能性があるため、要求する latency は 4 にとどめる（Windows で 45 ms が通った場合でも遅延は 225 ms）。

接続時のパラメータと更新結果は `CONNECT`／`CONN_PARAMS` のログで確認できる。

**2. BT コントローラの modem sleep を有効化する。** `CONFIG_BT_CTRL_MODEM_SLEEP=y` と低速クロックの選択（まず main XTAL、可能なら RTC slow clock）を設定する。接続維持中のアイドル電流を下げる本命。RTC slow clock は精度が低いため、sleep clock accuracy の設定を合わせて見直す。

**3. アドバタイズを段階化する。** 切断直後の 30 秒程度だけ現状の高速間隔にし、その後は 1〜2 秒間隔へ落とす。さらに一定時間（例: 10 分）つながらなければ停止し、ボタン押下で再開する。ボンドが一つもない初回起動でも同じ扱いにする。

**4. ボンド済み相手への directed advertising、または whitelist を使う。** 消費電力への直接効果は小さいが、不要な接続試行を減らせる。

**5. 送信電力を下げる。** `esp_ble_tx_power_set` で ADV と CONN を +3 dBm や 0 dBm へ。実使用距離で切断されないか確認する。

**6. 未使用の BLE 5.0 機能を無効化する。** Extended advertising などが有効だが使っていない。主に RAM と起動時間の削減。

**7. Battery Service の通知間隔を延ばす。** 30 秒でも軽微だが、60〜120 秒で十分。

### 3.2 ディスプレイと入力

**8. 暗転ではなく完全消灯する。** AMOLED は黒画素が消費しないため暗転でも効くが、パネルのドライバ回路は生きている。一定時間後に `M5.Display.sleep()` 相当でパネルを止め、ボタン・タッチ・BLE イベントで復帰させる。

**9. 消灯中はタッチコントローラも休ませる。** 消灯中はボタンだけで復帰する設計にすれば、10 ms ごとの I2C ポーリングを止められる。タッチ IC の割り込み復帰が使えるならそれでも良い。

**10. 暗転までの時間と暗転時の輝度を下げる。** 30 秒→10 秒、下限 15→5 などを設定項目にする。

**11. 既定輝度を一段下げる。** 既定はインデックス 2（140）。1（90）で十分か確認する。

**12. 点灯画素の面積を減らす。** AMOLED は点灯面積×輝度で消費が決まる。アイコンを小さく、白い塗りを避け、接続中アイドル時は小さなミュート表示だけ残す「最小表示モード」を設ける。

**13. ホスト側のミュート変化で毎回画面を起こさない。** 現在は Output 受信のたびに `wake()` する。要件 R4 と相反するため、点灯を短時間（2〜3 秒）にして再消灯する折衷案が現実的。

**14. 待機中アニメーションを消灯時に止める。** pending 中の 250 ms 更新は部分描画で軽微だが、消灯中は不要。

### 3.3 MCU・RTOS・電源系

**15. PM を有効化して DFS と自動 light sleep を使う。**（適用済み。DFS は使わず light sleep のみ。USB コンソールの扱いは§4.5 を見ること） `CONFIG_PM_ENABLE=y`、`CONFIG_FREERTOS_USE_TICKLESS_IDLE=y`、`esp_pm_configure` で max 240 / min 80 MHz、light sleep 許可。案 2 の modem sleep と組み合わせると、接続を維持したまま SoC が眠れる。注意点は二つ。USB Serial/JTAG コンソールは USB 接続中に light sleep を妨げるので、リリース構成ではコンソールを無効にするか、USB 未接続時だけ効くことを許容する。Octal PSRAM 使用中の light sleep は動作するが、実機での安定性確認が必要。

**16. PM が難しければ CPU クロックを静的に落とす。** 80 または 160 MHz にする。この用途の描画量なら体感差は小さい。

**17. メインループをイベント駆動に変える。**（適用済み）10 ms の `vTaskDelay` ではなく、通知をタイムアウト付きで待つ。操作中・最後の操作から1秒以内・振動中・USB 給電中は 10 ms、それ以外は 100 ms。

ただし単に周期を延ばすだけでは入力を取りこぼす。タッチ IC から読めるのは「今触れているか」だけなので、100 ms 周期では、触れてから離すまでが 100 ms 未満の速いタップが2回の読み取りの間に収まって消える。ボタンも同じ。そこで KEY.A（GPIO2）、KEY.B（GPIO1）、タッチ INT（GPIO13）を light sleep の起床要因と実行時の割り込みの両方に登録し、入力があれば待ちを即座に打ち切る（`src/app/InputWake.cpp`）。light sleep の GPIO 起床はレベル指定しかできず、ピンの割り込み種別を共有するため、割り込みは Low レベルで登録し、発火したハンドラ内で自分を無効化して、ピンが High に戻ってからループ側で再度有効にする。BLE イベントもキューに積んだ時点でメインタスクへ通知する。

**18. FreeRTOS tick を 1000 Hz から 100 Hz へ。** tickless idle があれば効果は小さいが、なければ割り込み回数が減る。

**19. ログレベルを WARN 以上にする。** 毎イベントの `status()` 出力を含め、シリアル出力の CPU 時間を減らす。

**20. 未使用電源レールを PMIC 側で切る。** M5Unified の設定で IMU・RTC・マイク・スピーカーは無効化済みだが、PMIC のレールが実際に落ちているかは別問題。実機では PMIC の電源設定（レジスタ `0x06`）が `0x1f` で、Grove 端子向けの 5 V 昇圧（BOOST_EN）が有効だった。Grove を使わないなら `M5.Power.setExtOutput(false)` で切れる見込み。充電 LED や状態 LED があれば消す。

**21. 長時間未接続なら deep sleep へ。** 例えば 10 分以上つながらなければボタン GPIO 復帰の deep sleep に入る。鞄に入れ忘れた場合の消耗をほぼ止められる。復帰はリブート扱いなので、共存構成の起動判定（`firmware::checkStartupEscape`）が UserDemo 側へ逃げないか確認する。

**22. さらに長い放置では電源オフ。** PMIC が対応していれば `M5.Power.powerOff()` で完全停止し、電源ボタンで復帰させる。deep sleep より確実。

**23. USB 未接続時に USB Serial/JTAG PHY を止める。** デバッグ不要時の待機電流を少し削れる。

**24. Wi-Fi をビルドから外す。** 起動していないので実行時電力はほぼ変わらないが、PHY 初期化と RAM を減らせる。

**25. PSRAM 依存を減らす（上級）。** 466×466 の 16 bit キャンバスが PSRAM 常時稼働の理由。部分描画と内部 RAM の小さなスプライトに置き換えれば、PSRAM の待機電流と 80 MHz バスの消費を落とせる。改修量が大きいので最後の手段。

**26. Flash と PSRAM のクロックを 80 MHz から 40 MHz へ。** 効果は小さく、描画が遅くなるので優先度は低い。

**27. 振動は現状のままで良い。** 20 ms の短い駆動なので無視できる量。

## 4. 測定の手順

StopWatch の電源 IC（M5PM1）は電圧しか読めない。M5Unified の電池電流の取得は M5PM1 に対応しておらず、燃料計チップもない。そのため電流は外付けの USB テスターで測り、ファームウェアは状態の固定と、自分で読める値の出力を受け持つ。

### 4.1 シリアルコマンド

USB シリアル（115200 bps）に1文字送る。既存の診断コマンドと重ならない文字を使う。

| キー | 動作 |
|---|---|
| `p` | `PWR` 行を1行出す |
| `L` / `l` | `PWR` 行の1秒ごとの出力を開始／停止 |
| `D` | 表示の固定状態を順に切り替える。通常 → 設定輝度 → 暗転輝度 → 輝度0 → パネル sleep → 通常 |
| `A` | アドバタイズの一時停止と再開を切り替える（未接続時のみ） |
| `X` | 表示とアドバタイズの上書きをすべて解除する |
| `R` / `r` | 電池電圧の記録を開始／停止（60 秒ごと、RAM に最新 24 時間分） |
| `O` | 記録を `DRAIN` 行で吸い出す |

`PWR` 行の例:

```
PWR t=1395 vbat=4208 vbus=5174 lvl=100 chg=0 disp=on bri=140 conn=1 adv=0 cpu=80 ext=0 slp=0 rst=1 hold=0 rec=0
```

| 項目 | 意味 |
|---|---|
| `vbat` / `vbus` | 電池電圧と USB 電圧（mV） |
| `chg` | 充電中なら 1（PMIC の G2 ピン） |
| `disp` / `bri` | 表示状態（`on`・`dim`・`dark`・`sleep`）と実際の輝度 |
| `ext` | Grove 向け 5 V 昇圧が有効なら 1（PMIC レジスタ `0x06` の bit3） |
| `slp` | 自動 light sleep が許可されていれば 1。USB 給電中は 0（コンソール維持のためロック） |
| `rst` | 直前のリセット要因（`esp_reset_reason()` の値。1=電源投入、3=ソフト、4=パニック、5=割り込みWDT、6=タスクWDT、7=その他WDT、8=deep sleep、9=ブラウンアウト） |
| `hold` | 測定用の上書きが有効なら 1 |
| `rec` | 電池電圧の記録中なら 1 |

`D` で固定しているあいだは、自動暗転と入力による点灯を止め、画面に `TEST MODE` を出す。出力はログレベルに関係なく出るので、ログを WARN に絞った後も使える。

### 4.2 前提

USB テスターの値が本体の消費を表すのは、満充電後に USB 側から本体へ給電される構成（電源パス）の場合だけである。2026-09-11 に確認済みで、満充電後は充電電流が乗らず、白画面の負荷がそのままテスターに現れた（§5）。確認に使った診断用のコマンドとシナリオは、確認後に削除した。

満充電前は充電電流が混ざるので、`chg=0` になってから測る。

### 4.3 USB テスターでの測定

1. 満充電にして `chg=0` を確認する。
2. 次を実行する。ポートは自動検出し、見つからなければ `--port COMxx` を付ける。pyserial が必要なので、入っていなければ PlatformIO 付属の Python（`~/.platformio/penv/Scripts/python`）で実行する。

   ```
   python tools/power_measure.py measure
   ```

3. スクリプトがシナリオごとに状態を切り替える。10 秒待ったあと、テスターの値の入力を求める。未接続と接続中の切り替えは画面の指示に従って PC 側で行う。
4. 結果は `logs/power-日時.csv` に保存される。§5 の表へ転記する。

シナリオは次の6つ。`--only 3 4` のように番号で絞り込める。

| # | 状態 |
|---|---|
| 1 | 未接続・アドバタイズ・設定輝度 |
| 2 | 未接続・アドバタイズ・暗転 |
| 3 | 未接続・アドバタイズ・パネル sleep |
| 4 | 未接続・アドバタイズ停止・パネル sleep（下限の目安） |
| 5 | 接続中アイドル・設定輝度 |
| 6 | 接続中アイドル・パネル sleep |

### 4.4 電池電圧の減り方での測定

USB 接続中は USB Serial/JTAG が動いているため、light sleep（案 15）の効果が出ない。電池駆動での効果はこちらで比べる。

1. USB 接続中に `R` を送って記録を始める。
2. USB を抜き、比べたい使い方で数時間置く。
3. USB を挿し直す。挿してもリセットはかからない。次を実行する。

   ```
   python tools/power_measure.py dump
   ```

4. `logs/drain-日時.csv` が保存され、状態ごとの電圧低下の傾き（mV/h）が表示される。

記録は RAM に1分ごと、最新24時間分を持つ。これとは別に、最初の32時間分を15分ごとに NVS へ保存する（2026-09-18 までは8時間分を5分ごと。電池持ちが24時間前後まで延びたので、それを超える幅にした）。RAM の記録はリセットや電源断で消えるが、NVS の記録は電池が切れても残る。`O` は RAM に記録があればそれを出し、空なら NVS の記録を出す。電池が切れるまで放置した場合は、再起動後の `dump` で NVS の記録が取れ、最後の記録から電源が落ちた時刻が15分の精度で分かる。

NVS の記録は、ボンド情報やアプリ設定と同じ名前空間 `mutehid` にある1項目（約 300 バイト）で、毎回上書きする。`R` で記録を始めると RAM と NVS の両方の前回分を消す。

電圧と残量の関係は直線ではないため、比較は同じ電圧帯（例: 4.0〜3.8 V）どうしで行う。

### 4.5 注意

- テスターの値は 5 V 側の電流である。電池側の電流とは、充電・変換回路の効率の分だけ違う。案の比較は同じ条件どうしで行う。
- `PWR` の出力自体も I2C 読み出しを1秒ごとに行う。測定中の条件はそろえる。
- **light sleep 中は USB Serial/JTAG が止まる。** 案15を入れた直後、USB をつないだままでも light sleep に入り、コンソールが落ちてポートを開くことすらできなくなった（「デバイスが機能していません」）。書き込みもできない。IDF はコンソールのためのロックを自動では取らない。
- そのためファームウェアは、VBUS が 4000 mV を超えているあいだ `ESP_PM_NO_LIGHT_SLEEP` のロックを保持する（`power::updateSleepLock`、1秒ごとに更新）。USB 給電中は眠らず、電池駆動のときだけ眠る。`PWR` 行の `slp` で状態が分かる。
- この結果、**案15の効果は USB テスターでは測れない**。電池駆動（§4.4）でのみ比較できる。
- USB からアクセスできなくなった場合は、KEY.B を押しながら起動して UserDemo へ逃がすと復旧できる。
- シリアルポートを開くときは RTS/DTR を立てないこと。USB Serial/JTAG はこの信号でリセットする。`tools/power_measure.py` の `open_port()` は正しく処理しているが、その場限りのスクリプトで `serial.Serial("COM11", ...)` と開くと実機がリセットし、RAM の記録が消える。

### 4.6 適用の順番

1. **無線と SoC のスリープ（案 1・2・15）。** 接続維持中のアイドル電流を下げる。
2. **消灯とポーリング停止（案 8・9・17）。** 画面と入力系の待機電流を下げる。
3. **未接続時の対策（案 3・5・21・22）。** 放置時の消耗を止める。
4. 各段階で実測値を§5 に記録し、効果の小さかった案は見送る。

### 前提確認（§4.2）の結果

**USB テスター方式は有効。** 2026-09-11 に満充電・未接続で測った。シナリオ7〜9は、確認のために一時的に追加した診断用コマンド（全面白・最大輝度の `W`、充電停止の `C`）で作った状態で、確認後にファームウェアとツールから削除した。

| # | 状態 | テスター | mW | chgen |
|---|---|---|---|---|
| 3 | パネル sleep | 58 mA | 300 | 1 |
| 7 | 全面白・最大輝度 | 160 mA | 821 | 1 |
| 8 | 全面白・最大輝度・充電停止 | 160 mA | 822 | 0 |
| 9 | パネル sleep・充電停止 | 60 mA | 311 | 0 |

- 全面白で 102 mA 増えた。テスターは本体の消費を反映している。
- 充電を止めても値は変わらなかった。満充電後は USB 側から本体へ給電され、充電電流は乗っていない。
- したがってシナリオ1〜6の差が小さいのは本当の差である。画面の大部分が黒なので表示の消費はほとんど変わらず、約 58 mA の大半は CPU と無線などの固定分と考えられる。

参考として、それに先立つ本体側の観測（ファームウェアは測定・診断コマンド入り、満充電、PC と接続中）:

| 状態 | vbus | vbat | chgen | g3 |
|---|---|---|---|---|
| 通常・輝度 140 | 5178 mV | 4206 mV | 1 | o0 |
| 全面白・輝度 255 | 5134 mV | 4206 mV | 1 | o0 |
| 全面白・充電停止 | 5132 mV | 4202 mV | 0 | o0 |

- 全面白で vbus が 44 mV 下がった。USB ケーブルとテスターを流れる電流が大きく増えたことを示し、USB 側が負荷を供給していると考えられる。
- 充電を止めても vbus はほぼ変わらなかった。満充電で充電電流はほぼ 0 と考えられる。
- 書き込み後も `chgen=1` だった。PMIC のヘッダはダウンロードモードで充電有効ビットが消えるとしているが、この個体では消えなかった。
- G3（CHG_PROG）は出力 Low で、UserDemo が起動時に設定する状態と同じだった。UserDemo との差は充電電流の設定の違いではない。
- `src` は定義外の `0x05` を返した。
- 以上から、シナリオ1〜6の差が小さいのは測定の失敗ではなく、表示と BLE の差が固定分に比べて小さいためと推定している。シナリオ7〜9のテスター値で確定させる。
